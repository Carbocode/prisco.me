# Project organization

Mandatory agent rules are in [AGENTS.md](../AGENTS.md), which requires reading this guide before changes. This guide describes current responsibilities and must be updated alongside structural changes. To place new code, first identify its owning feature in the table below, then its responsibility. Shared code retains an explicit owner.

Application code is organized by feature in `src/features`. A feature owns its pages, specialized components, models, and server operations. Create internal directories when needed; features do not need identical directory trees.

Technical documentation, agent instructions, and AI discovery resources are written in English. Public editorial content and interface text retain their intended language. Page metadata, JSON-LD content, and language declarations must remain consistent with the page they describe.

## Routes and shell

`src/routes` preserves the URL structure expected by TanStack Start. Routes define loaders, parameter validation, access protection, endpoints, and `head()`. Larger views are imported from `features/*/pages`.

Views read router data through `getRouteApi` without importing the route module. JSON-LD remains in `head()` through `scripts` and `children: JSON.stringify(...)`.

`src/app/root-document.tsx` owns the HTML document and global providers; `src/app/query-client.tsx` configures React Query. `src/router.tsx`, `src/server.ts`, and other framework entrypoints remain where configuration expects them. `routeTree.gen.ts` is generated by the router.

## Boundaries and dependencies

`src/config/site.ts` contains site identity and common settings. `src/lib` contains only cross-feature utilities; feature-specific logic stays in its `domain` directory or beside its consumer.

Domain models and pure functions do not depend on pages or React components. Components may use feature models and services. Code reused across features has an explicit owner. For example, the canonical document model and embeds belong to `content` and are also used by the editor. The public renderer does not import the Plate editor.

`*.functions.ts` exposes server functions and applies required access checks. Repositories, D1 connections, R2 access, and authentication configuration remain in server modules. Client components import the server function boundary without accessing repositories directly.

The article service is divided under `cms/server/articles`: queries, mutations, publication, revisions, relation hydration, and snapshots have dedicated modules. Connection configuration and public author data are separate to avoid circular dependencies.

## Components and larger modules

`src/components/ui` contains shadcn primitives. Functional sections use them directly under the rules in `AGENTS.md`. `layout`, `artwork`, `media`, and `data-table` hold components shared across the site. Components specific to one feature stay in that feature.

The article form lives in `cms/components/article-form`: the view composes fields, `use-article-form.ts` manages state and actions, and types, conversions, and revision comparison have separate files. The editor separates plugin configuration, nodes, dialogs, toolbar, and static palette data. The contact questionnaire separates its flow model from presentation.

Split modules by responsibility and dependencies. A view may remain large when composing many related fields. Avoid re-export files that obscure dependencies or mix browser and server modules.

## Styles, assets, and dates

### ARD discovery

`site/domain/ard.ts` describes only the public content API; the `/.well-known/ard.json` route serves the manifest with public CORS. The HTML document links it through `rel="ard"`; `robots.txt` exposes `Agentmap` and allows crawling the public content API. Do not list authenticated endpoints, drafts, private data, or nonexistent capabilities.

The implementation follows the publisher role in the [ARD v0.91 proposal](https://agenticresourcediscovery.org/spec/), rather than the registry role: it does not expose a federated `POST /search` service or claim MCP/A2A support. `application/json` describes the actual resource format. Keep the manifest and parameter descriptions synchronized with the API; publication does not guarantee indexing by external registries.

### Rendering

`src/styles.css` is the global entrypoint. Imports explicitly preserve cascade order: foundations, landscape, surfaces, content, motion, theme, and utilities. Content, editor, and home styles belong to their respective features. Home has its own CSS entrypoint and scene-based division.

Artwork sources stay in `public`. WebP caches are described by `scripts/static-artwork.json`, generated with `bun run assets:render`, and validated with `bun run assets:check`.

`src/lib/dates.ts` interprets public dates in the `Europe/Rome` time zone defined in `src/config/site.ts`, so server and browser produce the same day and year. Do not compute current values used in rendering during Worker module initialization.

## Validation

Tests live beside their implementation. `bun run ci` validates assets, formatting, lint, types, tests, migrations, and compilation. For structural changes crossing routes and server modules, also verify public navigation, authentication, CMS pages, and draft creation in an isolated local database.

Moving application files does not require changes to public URLs or database migrations.
